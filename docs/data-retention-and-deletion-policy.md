# Data retention and account/workspace deletion

FOR-23 decision record, 29 October 2026. Policy version **1**. The user confirmed:

* Call summaries, decisions, notes and actions remain until explicitly deleted, independently of raw transcript expiry.
* Account/workspace deletion revokes access immediately and allows **30 elapsed days** for recovery before purge.

Other lifetimes below are explicit implementation defaults for this issue. They are not claims about a deployed scheduler, provider backup configuration or a completed erasure. The pure contract is [`data-lifecycle-policy.ts`](../apps/forge/src/lib/data-lifecycle-policy.ts). It is browser-independent and performs no deletion. Review baseline: `10e93edb17da832a932018cd1e846b41bc5a8874`.

## What exists and what must change

* [Calls](../apps/forge/src/application/calls/calls.server.ts) defaults to 30-day transcript retention, configurable to 7/30/90/365 days. Its sweeper empties transcript text and clears the summary lease; it keeps summaries, decisions, actions and notes. [Calls documentation](calls.md) already distinguishes those classes. The policy preserves that distinction.
* [Agent input files](../apps/forge/src/application/agents/attachment-service.server.ts) default to 24 hours from upload; [artifacts](../apps/forge/src/application/agents/artifact-service.server.ts) default to 30 days from creation. Environment overrides exist. `sweep-agent-retention.ts` invokes these file sweepers, not conversation/event retention. Existing artifact reads check deletion, not the expiry clock: read-time expiry enforcement is still required.
* [`sweep-product-retention.ts`](../apps/forge/scripts/sweep-product-retention.ts) removes terminal workflow correlation/effect rows after 90 days, deleted teams after 30 days and unpromoted desktop drafts after 30 days. This does not implement account/workspace deletion or universal content retention.
* [Workspace settings](../apps/forge/src/components/workspace-settings.tsx) calls `authClient.organization.delete` directly. [Auth/schema](../apps/forge/src/lib/auth.ts) does not provide this policy's tombstone/checkpoint workflow. Some user references restrict deletion, while `call_notes.user_id` cascades. Those paths must be replaced/migrated in FOR-100 before promising recoverable account/workspace deletion. Database cascade alone cannot prove object, export, search or backup removal.
* Agent prompts/events and workspace security audit rows have no complete age-retention adapter evidenced here. API audit events also go to application logs. Backup/PITR, object-version and external processor retention have not been verified in this decision. FOR-38 must prove the configured recovery/expiry behavior.

## Lifetime matrix

Days mean exact 24-hour UTC durations. At the deadline, content is unavailable to normal reads/downloads even if physical cleanup is retrying. Sweeps cannot be the only access check. Reads, exports, search, events, caches and replay use the same clock. `null` in the pure contract means no age expiry; explicit resource/account/workspace deletion still applies.

| Data class / contract key | Lifetime and clock | Deletion and restore rule |
| --- | --- | --- |
| Raw call transcript — `call-transcript` | 30 days from call start by default; owner/admin may choose 7/30/90/365 | Clear transcript/speaker text and raw copies. Shortening applies immediately; increasing never restores already expired text. No new grace period for age expiry. |
| Call summary — `call-summary` | Until call/workspace deletion | Retained after transcript expiry; explicit deletion includes summary embeddings/snippets/caches and model-derived copies. |
| Call decisions — `call-decision` | Until call/workspace deletion | Same independent lifetime as summary. |
| Call actions — `call-action` | Until call/workspace deletion | Includes action text/owner labels/completion. A separately created canonical issue remains a separate resource; remove the inaccessible backlink, not the issue. |
| Call notes/follow-ups — `call-note` | Until note/call/workspace deletion | Shared workspace contributions survive author account deletion with author identity anonymized. Parent deletion includes notes. |
| Issues/comments/reactions, projects/milestones, initiatives, documents, shared views/settings, inbox — `workspace-content` | Until explicit resource/workspace deletion | Ordinary issue/team/resource deletion hides immediately, recoverable for 30 days where supported; purge after. Parent/account rules below take precedence. |
| Durable issue/comment/document files and promoted artifacts — `resource-file` | Lifetime of owning resource | Revoke immediately with owner access; purge all object versions/previews/indexes after recovery. Preserve a separately authorized surviving reference; never cross tenants to reuse bytes. |
| Profile, personal preferences, personal skills/views and private history — `account-profile-preferences` | Until field/account deletion | Account deletion removes personal data after recovery. Workspace deletion removes its scoped personal records, not unrelated accounts/workspaces. |
| Agent thread/messages/run content — `agent-conversation` | 90 days after last terminal conversation activity | Archive/read/replay never renews the clock. A new actual terminal turn establishes a new conversation inactivity deadline. Cancel active work on explicit deletion; scoped private history follows account deletion. |
| Agent/tool/model event payloads — `agent-event` | Same 90-day conversation deadline | Includes prompts, completions, tool inputs/results, event-stream copies and runtime session content. Redact expired file bytes/embedded payload copies at the earlier file deadline. |
| Agent conversation summaries — `agent-summary` | Same 90-day conversation deadline | Summarization never extends source conversation retention. Distinct from deliberately saved workspace documents. |
| Agent input file — `agent-input-file` | 24 hours from upload | Keep only while a live run demonstrably needs it; restrict to that run and reconcile before deletion. Do not offer expired files in ordinary downloads/history. |
| Generated artifact — `agent-artifact` | 30 days from creation | Same restricted live-run exception; deliberate promotion through a normal authorized file command creates a durable owning-resource reference, not a silent expiry extension. |
| Pending/unfinalized upload — `pending-upload` | 24 hours from upload intent | Delete orphan/multipart/staging bytes and release reservations; no recovery UI for an uncommitted upload. Finalize racing expiry must be atomic. |
| Completed export — `export-file` | 24 hours from successful export completion | Revoke immediately on loss of access or deletion of its source scope. Delete archive, staging and delivery cache; user-downloaded copies are outside Forge's control. |
| Failed/cancelled export staging — `failed-export-staging` | 24 hours from job terminal time | No downloadable success state. Crashed jobs must become terminal through lease reconciliation; a crash cannot retain staging forever. |
| Command/idempotency/approval evidence — `command-receipt` | 90 days after command is terminal and reconciled | Keep only minimal IDs/hashes/outcome; redact private result bodies when owning content expires/deletes. Unsettled effects require reconciliation before evidence removal, never replay as a new command after expiry. |
| Import manifest — `import-manifest` | 90 days after reconciled completion/cancellation/failure | IDs/checksums/checkpoints only; no embedded source bodies. Resume an unsettled import only after reconciliation. Source content follows its own class; staging follows pending-upload expiry. |
| Migration alias/deduplication mapping — `migration-alias` | Lifetime of mapped resource | Minimal source/destination IDs and hashes, not raw payload. On deletion retain only suppression identity under the deletion-receipt clock; no import/restore authority. |
| Business workflow correlation/effect history — `workflow-history` | 90 days from terminal completion (failed-to-start: terminal update) | Active/ambiguous effects must reconcile first. Provider Workflow history is separately configured to this ceiling; do not put private content in it. |
| Redacted operational/application/provider job logs — `operational-log` | 30 days from event | No transcript/body/token/signed-URL logging. Configure every sink; deleting a DB row does not remove log copies. |
| Security/audit events — `security-audit` | 365 days from event | Retain minimal pseudonymous IDs, action/outcome/time. On deletion remove identifying profile/IP/payload copies; no content-retention exemption. Restricted operator access only. |
| Deletion progress/completion receipt — `deletion-receipt` | 365 days from final deletion completion | Minimal subject/request IDs, times, checkpoints, counts and errors; no deleted body or recoverable credentials. Repeated requests do not reset completed retention clocks. |
| Server DB backups/PITR, object backup versions, replica/snapshot copies — `server-backup` | Maximum 35 days from original backup capture | Recovery only, inaccessible to ordinary product users. Copying/restoring a snapshot never restarts its expiry. Conservatively verify disappearance by 35 days after the last online purge checkpoint. |
| Browser legacy source/recovery/downloaded import backup — `local-import-backup` | No automatic TTL; separate explicit local cleanup after reconciliation | FOR-22 applies. Server deletion cannot remotely erase offline browser storage or a user-controlled download; those files are never silently re-imported. |

The existing 24-hour/30-day agent environment overrides remain configuration, not permission to bypass this launch contract. Deployments must use the selected defaults unless a versioned policy amendment explicitly approves another duration and tests it. There is no blanket indefinite hold: reconciliation exceptions are resource-scoped, access-restricted and operator-visible. Cancel stale runs and resolve ambiguous effects; retain only the minimum evidence needed, not an entire workspace. FOR-24 owns sweep freshness and purge service objectives; this decision does not invent a measured service SLA.

## Account versus workspace ownership

An account deletion request requires fresh authentication by that account through a dedicated confirmed flow; API keys, agents, another member and ordinary administrators cannot request it for someone else. A workspace deletion requires a freshly authenticated current **owner**, explicit workspace-name confirmation and a transactionally stable target ID. Permissions and sole-owner status are rechecked at execution. An account owning a workspace must transfer ownership or separately confirm that workspace's deletion first; account deletion never silently destroys other members' shared work or strands an ownerless workspace.

Account deletion immediately revokes Forge sessions, API keys, grants and run authority, and removes Forge's stored provider/BYOK secret material. Purge personal settings/private history and remaining identity/membership records after the recovery window. It preserves other members' workspace content, replacing the departed author's profile links/display identity with “Deleted member”. User text contributed to shared issues, documents, Calls notes and canonical work remains workspace content; this choice is disclosed before confirmation. Deletion is not a promise to detect and scrub personal information a user wrote into every shared text body. Revoke Forge-specific OAuth grants where supported; do not destroy a user's provider-wide API key used outside Forge. Recovery requires reconnection, not restoration of old secrets.

Workspace deletion covers every member's data **in that workspace**: definitions, issues/comments, planning/documents, inbox/subscriptions, Calls raw/derived data, team skills, private agent runs/events, model/connector credentials, files and previews, export snapshots, indexes, caches, queued jobs and webhook/replay effects. Keep other workspaces/accounts intact. Shared database encryption keys cannot be destroyed if needed by surviving tenants; expiry must cover all content copies and key backups without breaking unrelated data. Polar subscriptions must enter their recorded cancellation/termination workflow; deleting a customer-content row is not proof that charging stopped. Provider-held invoices and user/provider-owned copies have their own boundaries; no provider-side erasure is claimed by this policy.

## Deletion lifecycle and retries

1. **Confirm and revoke.** Validate current authority, fresh identity and explicit target confirmation. Persist a policy-versioned request/tombstone and stable deletion ID atomically with access revocation. Record the immutable `requestedAt`; repeated requests return it. Deny all ordinary routes immediately, invalidate sessions/keys/grants/caches/file access, cancel active runs/jobs, stop sync/export/event delivery and prevent stale signed links from bypassing authorization. A lone membership-row deletion is insufficient. Report success only once revocation is durable; uncertain responses retry by request ID.
2. **Recoverable until `requestedAt + 30 days`.** Retain access-restricted recoverable records; the subject is absent from search/lists and normal reads. A dedicated recovery route requires fresh proof of account identity or current authorized workspace ownership, independently of revoked sessions. A deletion receipt is not a login token. Cancellation is atomic against the request version and refuses once purge starts or the exact 30-day boundary is reached. Recovery restores only still-unexpired data and appropriate resource state; old credentials, sessions, links, invitations, sync jobs and subscriptions are not silently re-enabled. A reopened account/workspace needs fresh grants/connections.
3. **Purge due, then purging.** At the 30-day boundary recovery closes even if a worker is late. A leased worker claims the stable request/version and checkpoints: credentials/jobs; database content; object bytes/versions; search/caches; exports/staging; identity/membership/anonymization. Enumerate dependents before dropping parent rows or storage references. Scope every operation by immutable subject/workspace ID. Checkpoint a class only when every dependent has a verified outcome; a DB cascade or delete marker alone cannot attest physical bytes, old versions or a search index.
4. **Retry failures without restoring access.** Persist per-target cursors/attempts/errors and retry with bounded batches, jitter/backoff and stable effect IDs. A missing target is idempotent success; timeouts/unknown provider outcomes require reconciliation. A failed object deletion leaves its tombstone, storage reference and reservation evidence intact. Exhausted automatic retries become an actionable operator item, not completion. Operators resume the same request; retry never resets recovery, content TTL or backup age. Stale workers cannot mark a newer request restored/completed.
5. **Online data purged; backups pending.** All six checkpoint classes must complete. Record the last verified online-purge time; `backupExpiresBy` is that time plus 35 days. Block recovery and re-creation of the deleted IDs. Display separate online-purge and backup-expiry states instead of “all data deleted”. Minimal pseudonymous audit/receipts remain under their explicit clocks. Failures/missing expiry proof after the backup deadline require operator action.
6. **Completed only with backup evidence.** After that conservative 35-day boundary, verify every covered DB/PITR/object backup/replica contains no recoverable deleted data or has expired, then record `backupExpiryVerifiedAt`. Elapsed time alone cannot attest completion. Retain the minimal completion receipt for 365 days, then expire it. Infrastructure incapable of this ceiling fails FOR-38/FOR-100; this document does not silently certify it.

Age expiry does not receive a new 30-day recovery window. A resource deleted shortly before its ordinary expiry cannot extend that lifetime through trash/recovery. Scope deletion overrides “until explicitly deleted” rows in the matrix. Credential revocation remains immediate even though private content is recoverable for 30 days.

## Restore and re-import exceptions

Disaster recovery restores only into isolation. Before user access, replay the current independently protected deletion journal/tombstones and policy deadlines, suppress deleted identities/resource IDs and purge expired raw/derived/file/export content. Verify counts/checksums and the restore's maximum original snapshot age. Restoring old grants, connectors, queued jobs, signed links or database rows must not reauthorize deleted users or restart effects. Keep the deletion journal outside the failure domain of the snapshot being restored; retain suppression evidence at least through every permitted restore horizon. Snapshots older than the 35-day ceiling are not supported recovery sources.

Provider disconnect stops new ingestion and removes credentials, but it does not delete already imported Calls; explicit resource/workspace deletion does. Transcript expiry must not cause a later sync to refill the same call from a provider. Explicit call deletion retains a minimal destination-scoped suppression identity under the 365-day receipt clock; backfills cannot bypass it. After suppression expiry, ingestion still obeys the original call-start retention limit and a bounded backfill, never an unlimited historical replay. Summary/decision/action retention cannot regenerate a transcript.

FOR-22 requires a new ownership/destination/snapshot review for any deliberate local backup re-import. It cannot write into a deleted destination, reuse purged canonical IDs or silently overwrite a newer record. A user may explicitly create new content in a currently authorized destination from a copy they still control, with fresh IDs/manifest and provenance; that is a new import, not restoration of old credentials or erased server state. Old jobs, replay cursors and receipts never authorize that action. New account signup with the same email creates a new identity and cannot recover a purged account's data.
